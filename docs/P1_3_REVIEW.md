## 1. Ringkasan Eksekutif

P1.3 menetapkan domain model murni (*pure TypeScript domain*) untuk pengelolaan daur hidup masalah pelanggan (*complaint episode*), perutean dan penautan pesan ke episode (*message association*), penentuan kelayakan respons pertama (*firstResponseCandidate*), serta pencatatan audit.

Seluruh 11 poin acceptance criteria P1.3 telah dipetakan terhadap implementasi fungsi aktual dan dibuktikan melalui 26 unit test terarah pada `tests/domain/episode-lifecycle.test.ts`. Suite domain dan provider proyek secara keseluruhan mencatat 105 unit test lulus (0 gagal) pada review verifikasi independen sebelumnya.

Berdasarkan kepatuhan penuh terhadap kontrak PRD v2.1 dan ketersediaan bukti empiris yang lengkap dalam batas lingkupnya, task **P1.3 berstatus Selesai (Done)**.

## 4. Batasan Bukti dan Pemisahan Tanggung Jawab

Untuk mencegah overclaiming dan menjaga keakuratan dokumentasi:

1. **Aktor Domain vs Sesi Server:** Unit test domain menerima objek `actor` sebagai parameter input; membuktikan kepatuhan skema dan validasi tipe aktor, bukan membuktikan keabsahan cookie sesi browser. Sesi staf diekstraksi dari server session (`supabase.auth.getUser()`) pada wrapper `lib/application/staff-episodes.server.ts` berdasarkan review statis kode. Pengujian alur sesi end-to-end browser ditangani terpisah pada P0.4–P0.6.
2. **Lingkup Pembuktian Persistence P1.4 vs Domain P1.3:**
   - Skenario 4 persistence (`later event evidence adds a guard after GENERIC without a second reservation`) memvalidasi penambahan guard claim insiden, bukan pengujian flow reopen di database.
   - Tidak ada pengujian integrasi database eksplisit untuk inbound reopen pada suite persistence P1.4; logika asosiasi dan transisi inbound reopen dibuktikan pada pengujian unit domain P1.3.
3. **Immutability vs Mutasi Database:** Fungsi domain tidak pernah memutasi snapshot input. Peningkatan versi (`version = version + 1`) dan penulisan baris database dilakukan secara atomik oleh layer persistence dalam transaksi PostgreSQL.
4. **Reservasi Bukan Izin Dispatch:** Sesuai PRD §8, reservasi pada `outbound_intents` hanya mencatat draft balasan dengan flag `dispatchAuthorized: false`. Dispatch fisik ke API Telegram berada di luar scope P1.3 dan P1.4 (mengikuti P2/P3).
